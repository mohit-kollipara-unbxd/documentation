## 1. Mimir Site Config Params

These live in the Mimir configstore under the sitekey's configuration. They are read via `GetStringValues` / `GetBoolVal` / `GetIntVal` which checks API param first, then experiment config, then site config.

---

### `reranker.recommend`
- **Type**: boolean
- **Required**: yes
- **What it does**: Master switch that tells Mimir to call the Reranker service at all. Without this being `true`, the entire rec reranker node is skipped.
- **Where read**: `SkipRecReranker()` in `helper.go` line 246

---

### `reranker.recommend.platform`
- **Type**: string
- **Required**: yes
- **Values**: `semantic_search`, `unbxd`, `re`, `netcore`, `aap`, `ltr`, `segment_ranking`, `diversity_ranker`
- **What it does**: Tells Reranker which model/platform to call. For IQ Recs use `semantic_search` (maps to `hybrid_search` in Mimir's internal metadata).
- **Where read**: `RecReq()` in `rec_reranker.go` line 167

---

### `reranker.recommend.count`
- **Type**: int
- **Default**: `100` (but `DEFAULT_OFFLINE_RECOMMENDATION_COUNT = 1000` exists for offline use)
- **What it does**: Number of products Reranker should request from its underlying model. For IQ Recs set to `1000` so Olympus has enough products to return.
- **Where read**: `RecReq()` line 168-170

---

### `offline_recommendation`
- **Type**: boolean
- **Required**: yes for IQ Recs
- **What it does**: Enables offline recommendation mode in Mimir. Without this:
  - `SkipRecReranker()` returns `true` and the node is skipped for `q=*` or `p-id=*`
  - `PatchProductsToFq` gate will not fire even if filter is in API
  - `AddBoosts` will still run but the fq injection won't happen
- **Code reference**: `ENABLE_OFFLINE_RECOMMENDATIONS = "offline_recommendation"` in `const.go` line 577

---

### `user.offline_recommendation.filter`
- **Type**: string (can be multi-value, passed as repeated param or comma-separated)
- **Required**: yes (either in site config or API param — **location matters**, see mode table below)
- **What it does**: Lucene filter expression sent to Olympus's `filter_request` as the `filter` field. Only products matching this expression for the given uid are returned from Olympus. Examples:
  - `NormCode:001`
  - `SOQ:[0 TO 1] AND NormCode:001`
- **CRITICAL — case sensitive**: Olympus field names are case-sensitive. `NormCode` ≠ `Normcode`
- **Mode impact**:
  - If passed as **API param** → `offline_reco_mode = PATCH`, products injected into Solr `fq`
  - If in **site config only** → `offline_reco_mode = BOOSTED_PRODUCTS`, products only in `ub.map`
- **Where read**: `RecReq()` lines 191-198

---

### `user.offline_recommendation.boost`
- **Type**: string (multi-value)
- **What it does**: Secondary Olympus filter expression sent as `boost_request` to Olympus. Products matching both `filter` AND `boost` get an additional score on top (`filter_norm + boost_norm`). Products matching only `filter` get `filter_norm` only.
- **Example**: `SOQ:[0 TO 1] AND NormCode:001` (products with high order quantity and specific norm code)
- **Where read**: `RecReq()` lines 205-207

---

### `user.offline_recommendation.boost.norm`
- **Type**: float
- **Default**: `100` (for filter_norm), `200` (for boost_norm) — from `recommender.py` lines 468-469
- **What it does**: The score value assigned to each offline product coming from Olympus. This score ends up in `ub.map` and is used by Solr's `fieldcompare` function.
  - For **default** boost_type: products in `ub.map` get this score added to their Solr ranking
  - For **negative** boost_type: this value is **inverted** (`1 / norm`) before being used. So `norm=100` → multiplier of `0.01` → strong demotion
- **Where read**: `RecReq()` lines 208-210, `offline_recommender_v2.py` lines 93-94, 103

---

### `user.offline_recommendation.boost_type`
- **Type**: string
- **Default**: `default` (empty = default)
- **Values**: `negative`, or any other value (treated as default)
- **What it does**: Controls whether Mimir demotes or boosts products in `ub.map`
  - **default**: Uses Solr `bf` with `fieldcompare` function → adds score multiplicatively to boost offline products up
  - **negative**: Uses Solr `boost` (multiplicative factor) with `if(eq($fieldcompare_param,0),1,$fieldcompare_param)` → products in `ub.map` get their score as a multiplier. With `norm=100`, multiplier = `0.01` → effective 100x demotion
- **Side effects when `negative`**:
  - `enablePopularity` is forced to `false`
  - `user.behaviour` is forced to `false`
  - Both prevent existing UB/popularity boosts from interfering with the demotion logic
- **Where read**: `AddBoosts()` in `helper.go` lines 934-954, `configparams_builder.go` lines 125-130

---

### `user.offline_recommendation.promotion.additive`
- **Type**: string array (multi-value)
- **What it does**: Merchandising rules applied additively to the offline products' scores in Reranker before they are sent back to Mimir. Each rule is a conditional expression evaluated per product. Matched products get score adjustments added.
- **Example**: `if(SOQ >= 5, score * 1.2, score)` style rules
- **Mode note**: If passed as **API param**, it forces `patch` mode regardless of filter source (see `promoRulesFromAPI` logic at lines 176-198 of `rec_reranker.go`)
- **Where read**: `RecReq()` lines 176-188

---

### `user.offline_recommendation.promotion.multiplicative`
- **Type**: string array (multi-value)
- **What it does**: Same as additive promotion rules but applied multiplicatively. Allows scaling scores of specific product segments.
- **Mode note**: Same as additive — if passed as **API param**, forces `patch` mode
- **Where read**: `RecReq()` lines 176-188

---

### `reranker.recommend.patchProducts`
- **Type**: boolean
- **What it does**: Enables `PatchProductsToQuery` — injects top-N offline products into the Solr query using `OR` logic (not `fq`). Unlike `fq` (AND), OR doesn't restrict results — it just boosts matching products. Used for text search queries where products must match query terms but should be surfaced.
- **Requires**: `tokenCount > minTokenCount` AND `len(recResp.Products) > 0`
- **Where read**: `handleRecResponse()` line 109

---

### `reranker.recommend.patchProducts.count`
- **Type**: int
- **Default**: `10`
- **What it does**: How many products to inject into the Solr query when `patchProducts` is enabled. Only the top-N products from `recResp.Products` are used.
- **Where read**: `handleRecResponse()` lines 110-118

---

### `reranker.recommend.patchProducts.minTokenCount`
- **Type**: int
- **Default**: `-1` (disabled)
- **What it does**: Minimum token count in the query for `PatchProductsToQuery` to fire. Prevents injecting products for very short/single-token queries. E.g. set to `2` to only patch for 2+ word queries.
- **Also used in**: `SkipRecReranker()` for hybrid search token count check
- **Where read**: `handleRecResponse()` line 101, `SkipRecReranker()` line 221

---

### `dynamic_fields` (under olympus handler)
- **Type**: boolean
- **What it does**: Enables the dynamic fields node which calls Olympus with the Solr result product IDs to patch user-product features (like `NormCode`, `SQ`, `SOQ`, `BP`) onto each product in the search response.
- **Important**: This calls Olympus with the **Solr result PIDs**, not offline PIDs. So if offline products are not in Solr results (e.g. they weren't injected via `fq` or `patchProducts`), their features won't be patched.
- **Where read**: `DynamicFieldsReq()` in `dynamic_fields.go`

---

### `reranker.norm`
- **Type**: float
- **Default**: `100`
- **What it does**: Global normalisation factor applied to the primary recommender model scores (from `semantic_search`, `aws`, etc.) before returning to Mimir. This is separate from `user.offline_recommendation.boost.norm`. The formula in Reranker is `norm * score / max_score`.
- **Where read**: `RecReq()` lines 201-203, `recommender.py` line 450

---

## 2. Mimir API Params (URL)

These are passed in the search API URL query string. Read via `GetStringAPIValues` which only reads from HTTP params (not site config).

---

### `uid`
- **Type**: string
- **Required**: yes for IQ Recs
- **What it does**: User ID passed to Reranker and then to Olympus to look up `user_product` features. Without a uid, Olympus returns nothing and offline recs produce empty results.
- **Where read**: `r.UID()` in `rec_reranker.go` line 233

---

### `user.offline_recommendation.filter`
- **Type**: string (multi-value)
- **What it does** (as API param): Same filter logic as site config BUT forces `offline_reco_mode = PATCH`, which means:
  1. Reranker merges offline products into primary `Products` list
  2. Mimir calls `PatchProductsToFq` → adds a Solr `fq` restricting results to ONLY offline product IDs
- **Warning**: With `q=Dove`, fq AND query text logic means only offline products matching "Dove" text return. For category/`q=*` this works perfectly.
- **Where read**: `RecReq()` line 191, `handleRecResponse()` line 106

---

### `user.fields`
- **Type**: string (comma-separated)
- **Required**: for dynamic fields patching
- **What it does**: Tells the dynamic fields node which Olympus features to fetch and patch onto response products. Example: `NormCode,SQ,SOQ,BP,VG,PRP`
- **Where read**: `DynamicFieldsReq()` in `dynamic_fields.go`

---

### `user.offline_recommendation.boost_type`
- **Type**: string
- **Values**: `negative`
- **What it does** (as API param): Same as site config — enables negative/demotion mode. Commonly passed in API when doing OOS demotion alongside `demoteQuery`
- **Where read**: `RecReq()` lines 211-213

---

### `user.offline_recommendation.boost.norm`
- **Type**: float
- **What it does** (as API param): Overrides the site config norm. In negative mode, `1/norm` is the demotion multiplier. Higher norm = stronger demotion.
  - `norm=2` → multiplier `0.5` → weak demotion
  - `norm=100` → multiplier `0.01` → strong demotion
  - `norm=1000` → multiplier `0.001` → very strong demotion
- **Where read**: `RecReq()` line 208

---

### `demoteQuery`
- **Type**: string (Lucene query)
- **What it does**: A Solr subquery parameter (named reference) used to identify a set of documents (e.g. OOS products). Used in the `boost` function as `query($demoteQuery)`.
- **Example**: `demoteQuery=sellerStockStatus307_unx_d:0`
- **Important**: `demoteQuery` by itself does nothing — it only works when referenced inside `boost=if(eq(query($demoteQuery),0),1,0.1)`. But the `boost` param is ignored by Mimir (see gotchas).

---

### `boost` (Solr)
- **Type**: string (Solr function)
- **IGNORED BY MIMIR**: `boost` is in `DEFAULT_BREWER_IGNORE_CONFIGS = ["emf", "emf.score", "bf", "boost"]`. Mimir strips this from the request before it reaches Solr. Any `boost=if(...)` in the URL has **zero effect**.
- **To make it work**: The `boost` function must be set in site config, not API param.

---

### `user.offline_recommendation.promotion.additive`
### `user.offline_recommendation.promotion.multiplicative`
- **What it does** (as API param): Same as site config but when passed as API param, **forces `patch` mode** even if `user.offline_recommendation.filter` is not in API params. This is the `promoRulesFromAPI` logic.
- **Where read**: `RecReq()` lines 176-198

| `offline_reco.merchandising_rules.multiplicative` | string[] | `[]` | Multiplicative scoring rules |

## 4. Olympus Params (Internal)

These are what Reranker sends to Olympus. Not directly configurable from Mimir API, but shaped by the params above.

**Batch payload structure:**
```json
{
  "filter_request": {
    "uid": "<uid>",
    "features": "*",
    "products": [],
    "filter": ["<user.offline_recommendation.filter values>"],
    "feature_group": "user_product"
  },
  "boost_request": {
    "uid": "<uid>",
    "features": "*",
    "products": [],
    "filter": ["<user.offline_recommendation.boost values>"],
    "feature_group": "user_product"
  }
}
```

- **`filter_request`**: Always present. Returns all user_product features for the uid matching the filter. Each returned product gets `score = filter_norm`.
- **`boost_request`**: Only present if `user.offline_recommendation.boost` is set. Returns products also matching the boost filter. These get `score = filter_norm + boost_norm` (overlapping products get both).
- **`PRP_MAX`**: Olympus can return a metadata field `PRP_MAX` which Reranker uses in merchandising rules.

---

## 5. Solr Params Generated by Mimir

These are what Mimir actually sends to Solr (Brewer) based on the above config:

| Solr Param | When set | What it does |
|-----------|---------|-------------|
| `ub.map` | Always when offline products exist | JSON map of `{"boostData": {"<productId>": <score>, ...}}`. Contains products from both `recResp.Products` AND `recResp.BoostedProducts` (merged, deduped in `Boosts()`) |
| `bf` (default mode) | When `boost_type != negative` | `fieldcompare(uniqueId,<ub.map>)` — adds score from ub.map to product relevance score |
| `boost` (negative mode) | When `boost_type = negative` | `if(eq($fieldcompare_param,0),1,$fieldcompare_param)` — multiplies score by the ub.map value. With inverted norm, products in ub.map get a tiny multiplier → demoted |
| `fieldcompare_param` | When `boost_type = negative` | `fieldcompare(uniqueId)` — the lookup param for the boost function |
| `fq` | When `offline_recommendation=true` AND `user.offline_recommendation.filter` is in API | `uniqueId:("id1" OR "id2" OR ...)` — hard restricts results to offline product IDs only |
| `enablePopularity=false` | When `boost_type = negative` | Disables popularity boosting to prevent interference |
| `user.behaviour=false` | When `boost_type = negative` | Disables user behaviour UB scoring to prevent interference |
| `ignore.config` | Always | `["emf", "emf.score", "bf", "boost"]` — strips these from any API-provided values |

---

## 6. Mode Decision Table

| `user.offline_recommendation.filter` source | `offline_reco_mode` | Reranker response | Mimir action | Solr effect |
|---|---|---|---|---|
| **API param** | `PATCH` | Products merged into `recResp.Products` | `PatchProductsToFq` → adds `fq` | Results restricted to ONLY offline product IDs |
| **Site config only** | `BOOSTED_PRODUCTS` | Products in `recResp.BoostedProducts` | `AddBoosts` only | Offline products boosted via `ub.map` within organic results |
| **API param + `promoRulesFromAPI`** | `PATCH` forced | Same as PATCH | Same as PATCH | Same as PATCH |
| **Site config + `promoRulesFromAPI` from API** | `BOOSTED_PRODUCTS` | Products in `BoostedProducts` | `AddBoosts` only | Same as BOOSTED_PRODUCTS |

**When to use which mode:**

| Use case | Recommended mode |
|----------|-----------------|
| Category page `q=*`, browse all, show personalized recs | `boosted_products` (filter in site config) |
| Category page, show ONLY offline recommended products | `patch` (filter in API param) |
| Search page `q=Dove`, boost user's preferred Dove products | `patch` (filter in API param, products must match "Dove" too) |
| OOS demotion (negative boost_type) | `boosted_products` (filter in site config, boost_type=negative) |

## 7. Important Gotchas

**1. `boost` API param is always ignored**
`DEFAULT_BREWER_IGNORE_CONFIGS = ["emf", "emf.score", "bf", "boost"]`. Never pass `boost=if(...)` in URL expecting it to work. Must be in site config.

**2. Olympus field names are case-sensitive**
`NormCode` ≠ `Normcode`. A wrong case means Olympus returns 0 products → empty offline recs → ub.map empty → nothing changes in results.

**3. `boost_type=negative` is NOT global OOS demotion**
It only demotes products that are specifically in the user's Olympus offline product set (in `ub.map`). OOS products outside that set are completely unaffected and rank normally.

**4. `patch` mode + text query = high risk of 0 results**
When `user.offline_recommendation.filter` is in API param, Solr gets an `fq` that restricts to offline product IDs. If `q=Dove`, Solr AND-s the text query with the fq. Offline products not matching "Dove" text are excluded → could return 0 results.

**5. Dynamic fields only patch what's in Solr results**
`dynamic_fields` node fetches features for Solr result product IDs. If offline products never entered Solr results (because they weren't injected via fq or patchProducts), their `NormCode`/`SOQ`/etc. won't appear in the response.

**6. `PatchProductsToQuery` vs `PatchProductsToFq`**
- `PatchProductsToFq`: hard filter via `fq` — only acts on `recResp.Products` (patch mode)
- `PatchProductsToQuery`: soft OR inject into query — only acts on `recResp.Products` (not BoostedProducts)
- `BoostedProducts` (boosted_products mode) **only reaches Solr via `ub.map`** — never via fq or query injection

**7. Reranker is skipped for `q=*` unless `offline_recommendation=true`**
`SkipRecReranker()` has a special condition: `(len(q) > 0 && q != "*") || offline_recommendations`. Without `offline_recommendation=true` in site config, wildcard queries skip the rec reranker entirely.

**8. norm inversion in negative mode**
In `offline_recommender_v2.py`:
```python
if boost_type == 'negative':
    boost_norm = 1/boost_norm if boost_norm else 0.01
    filter_norm = 1/filter_norm if filter_norm else 0.01
```
So `norm=100` in site config → Reranker stores `0.01` as the score in `ub.map` → Mimir's `if(eq($fieldcompare_param,0),1,$fieldcompare_param)` means matched products get `0.01` multiplier on their score.


# IQ Recs — API Query Parameters Reference

> Assumes site config (`offline_recommendation`, `reranker.recommend`, `dynamic_fields`, etc.) is already set up in Albus. This doc covers only the **query params you pass in the search URL**.

---

## Quick Example

```
https://search.unbxd.io/{apikey}/{sitekey}/category
  ?p-id=*
  &uid=4484136
  &user.fields=NormCode,SOQ,SQ,BP
  &user.offline_recommendation.filter=NormCode:001
  &rows=50
```

---

## The Params

### `uid` — **required**
The user identifier. Olympus uses this to look up the user's `user_product` features. Without it, offline recs are empty.

```
uid=4484136
```

---

### `user.fields`
Comma-separated list of Olympus features to **patch onto each product** in the search response (via the dynamic fields node).

```
user.fields=NormCode,SOQ,SQ,BP,VG,PRP
```

Each returned product will include these fields inline. If the feature doesn't exist for a product in Olympus, it's omitted.

---

### `user.offline_recommendation.filter`
Olympus filter expression. Returns the user's personalised products matching this criteria.

**Passing it as an API param switches the flow to `patch` mode** — results are restricted (via Solr `fq`) to only these offline product IDs.

```
user.offline_recommendation.filter=NormCode:001
user.offline_recommendation.filter=SOQ:[0 TO 1] AND NormCode:001
```

- Field names are **case-sensitive** (`NormCode`, not `Normcode`).
- Best suited for `q=*` / category browse. With a text query (`q=Dove`), results are further AND-ed with the text match — can yield empty results.
- If omitted from the URL, Mimir falls back to the site config value (in `boosted_products` mode — recs are boosted alongside organic results).

---

### `user.offline_recommendation.boost_type`
Controls whether IQ Recs products are **promoted** or **demoted** in ranking.

| Value | Behaviour |
|---|---|
| *(omit)* | Default: offline products are boosted to the top |
| `negative` | Offline products are demoted (pushed down) |

```
user.offline_recommendation.boost_type=negative
```

When `negative` is set, Mimir also auto-disables `enablePopularity` and `user.behaviour` for this request to prevent them from overriding the demotion.

---

### `user.offline_recommendation.boost.norm`
The score magnitude for offline products. Interpretation depends on `boost_type`:

| Mode | Effect of `norm` |
|---|---|
| Default boost | Higher norm = stronger promotion |
| `negative` | Multiplier becomes `1/norm` — higher norm = stronger demotion |

```
user.offline_recommendation.boost.norm=100
```

**Negative mode cheat sheet:**

| norm | multiplier | strength |
|---|---|---|
| 2 | 0.5 | weak — halves score |
| 10 | 0.1 | mild |
| 100 | 0.01 | strong |
| 1000 | 0.001 | very strong |

---

### `user.offline_recommendation.promotion.additive`
Merchandising rules applied **additively** to offline product scores in Reranker. Multi-value.

```
user.offline_recommendation.promotion.additive=if(SOQ>=5,score*0.2,0)
```

Passing this **forces `patch` mode** even if `user.offline_recommendation.filter` is only in site config.

---

### `user.offline_recommendation.promotion.multiplicative`
Same as additive, but rules are applied **multiplicatively**.

```
user.offline_recommendation.promotion.multiplicative=if(NormCode:001,1.5,1)
```

Also forces `patch` mode when present in the URL.

---

## Gotchas Worth Knowing

**1. `boost=if(...)` in the URL is ignored.**
Mimir strips the Solr `boost` param (and `bf`, `emf`, `emf.score`) from every request. If you need custom boost/demote logic, it must go into site config — passing it via URL does nothing.

**2. `boost_type=negative` only demotes offline products.**
It is **not** a global demotion. Only products that Olympus returns for this uid (i.e. products in `ub.map`) are affected. Any other product — including OOS items not in the user's offline set — ranks normally.

**3. `patch` mode + text query = risk of empty results.**
When `user.offline_recommendation.filter` is in the URL, Mimir hard-filters results to the offline product IDs. Combined with `q=Dove`, Solr returns only offline products that also match "Dove" in their text — often zero.

**4. Dynamic fields only patch products present in the Solr result set.**
If an offline product isn't in the response (e.g. didn't make the page), its `user.fields` won't appear either.

**5. Olympus field names are case-sensitive.**
`NormCode:001` returns data; `Normcode:001` returns nothing. Silent failure — `ub.map` will just be empty.

---

## Mode Quick Reference

| Where `user.offline_recommendation.filter` lives | Mode | Result |
|---|---|---|
| **URL param** | `patch` | Results restricted to offline product IDs (Solr `fq`) |
| **Site config only** | `boosted_products` | Offline products boosted within organic results (via `ub.map`) |
| **Not set anywhere** | — | No IQ recs applied |
